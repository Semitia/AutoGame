# 架构与扩展约定

目标是支持多个平台、多个游戏。当前只抽离已经复用的设备能力，不把游戏坐标、角色配置或战斗状态机包装成通用能力。

## 当前边界

`src/autogame/platforms/base.py` 定义截图、点击、拖动、显隐接口。`MuMuPlatform` 用 ADB 返回 PNG 字节并执行安卓输入，用 MuMuManager 控制窗口；不认识英雄、关卡或体力。

`games/bilibili_hero_merge/farmer.py` 是当前游戏的视觉基础：1080×1920 截图归一化为 432×768，模板匹配、格子占用判断和日志。旧 stage-35 主循环已经从活跃代码中移除，原文件保存在本地迁移归档。

`vision.py` 负责 OCR 和边框评分；`policy.py` 是纯策略；`strategic.py` 编排观察、决策、执行、确认、增量修复和结算。`strategy.json` 定义角色、保留数量、buff 顺序及下一次费用比例。

`run.py` 通过显式游戏注册表分发。当前游戏仍直接使用 MuMu 适配器以及 Windows 文件锁；这次迁移没有宣称已完成跨平台通用调度器。

## 添加游戏

1. 建立独立 `games/<game_id>/`，添加识别模板、策略配置、状态机和测试。
2. 复用平台适配器；不要把游戏坐标或规则放进平台层。
3. 在 `run.py` 注册入口；运行产物写入 `runtime/<game_id>/`。
4. 先验证一局的开始、结算、恢复和停止，再开启循环。

## 添加平台

实现 `GamePlatform` 协议；如浏览器、其他模拟器有不同输入语义，在适配器内转换。游戏使用自身坐标映射。通用任务配置、平台选择和插件发现机制留待第二个实际实现出现后提取，避免先构建空框架。

## 状态和纠错

镜像记录格子、角色、阶级、召唤次数、待确认动作和修复标记。操作后观察再确认；未知阶级为 0，排除合成。每隔至少 12 秒检查一个格子，同格至少间隔 45 秒。修复不承诺重新读出阶级，不能保证完整重建任意中途棋盘。

文件保存先写临时文件再替换，失败短暂重试，持续失败则保留内存并于稍后重试。状态持久化失败时，进程重启恢复可能落后于实际画面；不要将其误解为无损恢复。
