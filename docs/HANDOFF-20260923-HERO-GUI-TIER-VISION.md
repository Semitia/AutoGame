# Handoff：蔚蓝星球 GUI、技能库、合作调试与阶级识别

日期：2026-09-23。此文用于下次继续开发，区分用户说明、截图实验、已接入行为与未完成设想。运行状态必须重新核实，不复用此文设备编号或旧棋盘坐标。

## 1. 用户目标与最终授权

- 从玩家角度使用 GUI：关卡、模式、双方阵容、战术放主界面；环境和文件路径移到设置。环境通常不变。
- 主线 34 关不是独立玩法，已合并到主线关卡配置。
- 同时打开两台模拟器时，要能选择并认出每台设备；不要求玩家理解 emulator 编号。
- 下拉框和数值框不应因页面滚轮误改；技能顺序应拖动调整，不应重复手输。
- 战斗发现技能后自动记录；未认领列表必须直接展示标题和完整描述，不用悬停。双击认领只取标题、用默认命名、不再确认；已认领可退回公共池。
- 阶级识别最初仅做离线/日志实验。**最后用户明确要求先接入用于救急，接受不够准确的识别**，因此本次把候选阶级接入未知阶级修复及合成策略。不可继续宣称“全部只记日志”。
- 用户要求详细记录讨论、设想、尝试并 commit 本轮改动。没有要求本次重开游戏测试；本次接入只做自动化测试，未启动实战。

## 3. GUI / 技能库交接重点

GUI 使用深色 Qt 卡片，不再是 Tkinter 表单。四英雄卡包含职责、保留数量、选卡顺序、可拖动技能优先级。合作上下展示两套配置。配置会自动保存，运行时使用快照，编辑不会污染已启动进程参数。

设备发现只做查询；通过 MuMu 实例信息与 `/proc/sys/kernel/random/boot_id` 核验，而不是按编号大小猜身份。下拉显示友好名称，itemData 保留真实 ADB serial。用户切换模式/配置或设备刷新不应清空已选设备。

技能库模型：heroes、skills、preferences、observations、claims、returned_skills、library_migrations。raw OCR 文本保留标题加描述；认领键是原始文本，正式技能取第一个空白分隔标题。OCR 的跨行拼接可能导致错字或标题边界错误，尚未做完整的卡片版面分割。退回 tombstone 防止旧配置 seed 又把技能自动认领回来。未认领列表显示“标题\n详细描述”，自动换行、不省略；tooltip 不是唯一描述入口。

曾错误地把“认领只取标题”理解成“列表只显示标题”，用户纠正后已恢复完整描述。不要再次隐藏描述，也不要恢复双击确认弹窗。GUI 实际窗口已检查，相关回归测试覆盖滚轮、认领/退回、名称和描述分离。后续 UI 手工验证注意测试窗口和用户真正 pythonw 窗口不同，重启前先让编辑保存。

## 4. 合作实战调试的事实与边界

历史实测当时：实例1 / emulator-5556 为踏实的龙利鱼（71服）；实例0 / emulator-5554 为幽美的竹笋（37服）。原配置“优美”误写，正确是“幽美”。昵称蓝色是自己、红色是对方；旧反判已修正，旧截图文件名不能当身份真值。

用户曾手动接管竹笋，又允许代理调试龙利鱼及必要时接管竹笋。脚本观察遇特效，不应马上把所有格子判不可信；现对不稳定棋盘连续拍三帧，每格至少两票且不允许占用/空冲突。已知格消失不能直接沿用旧占用。处于战斗但观察不稳可等待60秒，未知界面保持20秒限时。

初始空棋盘可能召唤费10，而非总是免费。允许首波七空格+价格10初始化；显式 `--adopt-empty` 只用于确认未动过的七空格初始盘，不是任意战斗接管。

当时监督合作第二层在第10波失败，用户操作竹笋、临时辅助脚本补充操作；不能把这个过程说成完整自动通关。一次临近结算的合成手势成功与否未证实。所有后续阶级工作是离线实验。重开前按 AGENTS 和 BLUE-PLANET-MEMORY 读实时状态、设备与进程锁；正在战斗不得插入另一个控制器。

## 5. 阶级规则与用户提出的算法路线

用户说明：1/2/3阶对应同一格里1/2/3个小人，4阶变单个大人。皮肤和英雄外观很多，逐个收集完整头像模板不理想。

用户提出：

1. 与默认空格相比差异明显，或单击出现人物详情，可以判断格内有人。
2. 确认占用后只在这个格内搜重复子区域；同一组小人外观相同，不需先知道英雄名字。
3. 单个小人再通过大小区分一阶和四阶。
4. 同格动作应该同步，因此不应过度以动画差异否定自相似。
5. 三人后排可能遮挡，但前两个仍可见；武器、狼牙棒等露出的片段可以作为第三人的证据。
6. 三人前排比二人更靠下；应以人物整体/重心位置判断，不能直接把装饰物、头盔或某个 part 的位置当成人物位置。

上述是设计依据。截图的高相关支持同格重复假设，但尚未录制视频证明所有动画阶段同步；前排永不被遮挡也没有对所有技能特效实测。未实现“点击详情 → 自动计数”的新闭环；现有 identify 点击只验证英雄身份。不得将设想写成已经完成的能力。

## 6. 尝试 A：预制头部模板

`tier_vision.py`：对已定位格子裁剪 x±0.53格距、y-0.93～+0.16格距。在7个外观模板上做约0.72～1.84尺度、-20/-10/0/10/20度旋转的 TM_CCOEFF_NORMED，阈值0.61，再按0.23格距去重。二人水平、三人三角；单人按模板相对尺度判断一/四阶。score 是相似度，不是正确概率。

模板来自用户原图：骑士/侧向骑士、绿帽人物/大绿帽人物、紫杖人物/正面紫杖、红发人物。外观名不等于英雄身份。

原图9/9，但模板来自同一图，是开发拟合，不能算独立准确率。另一张战斗图最初汇报“5组认对4组、1组未知”，用户指出还有四个一阶没识别。实际完整分母是8组英雄：4正确、4未知，另1空格未知。原汇报漏了底排冰法和第二个小炮，还只挑选了支持的目标；已纠正标注与文档，今后必须汇报完整分母。

头部遮挡压力测试会把三人红发组当成二阶。三帧一致工具只防暂时波动，不能消除持续遮挡的系统性错误。旧 `--trace-tiers` 仍是独立的诊断日志开关，不是新默认救急开关。

## 7. 尝试 B：空格差分 + 格内自相似

`tier_structure.py` 将格子规范到96×101像素，裁剪约x±0.5、y-0.95～+0.1格距。使用同屏已确认空格参考，去除中位颜色偏移，再以差分>32和形态学开运算提取前景。输出 occupied 和 tier 两个不同字段，避免“阶级未知=没人”。

搜22/28/34像素有纹理且有前景的块，在左右对应区域匹配。二阶候选阈值0.80；三角第三副本联合相似度0.77。若无重复且前景窄于0.65格距，给紧凑单人一阶候选；宽大前景不直接认四阶，因为武器/光环也会扩大外形。

第一次全高搜索把上方格子边缘误当成重复人物，导致底排冰法/小炮报二阶；现二人种子只来自规范图y47～66的前排区域，后排只做向上查找。该限制有避免上方邻格污染的目的，但也解释了为何早期只画头盔、没有独立搜狼牙棒：只保留一个最高分块，而且武器上方区域没有作为二人种子。**没画框不等于武器不存在或无法匹配。**

二/三阶识别后，自动提取同屏小人局部，跨尺度、少量旋转尝试一/四阶大小校准。不会读取标注 expected 或英雄头像库。此步骤仍未认出原图四阶游侠，保持未知。

初版结果：战斗图8/8阶级吻合、8/8占用；原图8/9阶级吻合、9/9占用。战斗图的空格本身也是背景参考，不能把自比较判空当成空格泛化准确率。这两张图都参与调整新算法，均不是新方法的独立测试集。

## 8. 尝试 C：多部件前景与前排下移

用户指出局部块不是人物重心后，新增 `pair_geometry`：固定左右平移，汇总多个10×10有纹理且有前景的对应区域，要求垂直覆盖，不允许只靠一个眼睛/饰物定义位置。记录 pair_support、pair_center_y。这仍是可见纹理前景，**不是人体语义分割、脚底或真实重心**。

测量发现二阶骑士与三阶红发的前景中心会重叠，不能设全英雄通用的单一高度阈值。于是加入同屏参照 `align_pair`：按前排间距归一尺度，多块身体纹理共同估计平移；下部身体覆盖高度至少18规范像素，部分匹配>=0.82、总体中位>=0.78等只是经验阈值。

跨格红发二人/三人并非原尺寸完全相同，直接平移匹配失败；按间距41/45调整尺度后，多块纹理才对应。下移>=6/96格距时，只把二阶降为未知，reason=`lowered_pair_possible_occluded_third`，不直接判三阶。布局校验只提供否定二阶的证据。

可复现遮挡：原图 `image[150:216,716:801]=(150,150,150)`。遮挡后三阶红发组在孤立单格方法中仍报二；同屏布局校验现在返回未知，测出前排下移约0.086格距。它没有“看见”第三人，只是避免把两个可见副本当成恰好两人。

代价：战斗图右侧真正的二阶骑士也被保守拦截。因此最新纯结构结果是战斗图7正确/1未知，原图8正确/1未知，不是仍然8/8。不同格子可能动作不同，不能把用户的“同格同步”推广到跨格同步。当前测试明确覆盖这个误拦截，不用修改真值掩饰。

仍未完成：独立武器检测、后排零碎部件聚合、真正人物重心/脚底定位、时间序列轮廓融合、独立皮肤泛化验证。尝试不是最终算法，不能宣传成通用人数识别。

## 9. 本次默认接入行为

`TierRescue.recover` 只处理已确认 hero、tier=0、未标 uncertain 且当前仍占用的格子。操作记录已有1～4阶不覆盖；unknown hero 不凭图猜名字；待验证的召唤/合成不走识图修复，以免用预测给失败操作自证成功。

算法顺序：整盘结构候选 → 未知时原头部模板兜底 → 仍未知保留0。**即使结构层因前排位置而保守弃权，模板也可以在救急模式下给候选**；这是用户接受不准后的折中。记录 `visual_tier_recovery` 的 cell、hero、method、tier、applied、两种完整证据；写入 unit.tier_source=`visual:structure` 或 `visual:head_template`。合成仍要求策略中的同英雄同阶、保留数量、合法棋盘和普通动作验证。

空格参考来自本次检测的空位，保存在该运行对象；没有空位且没有已缓存背景时结构返回未知、转模板，不把任意格当空。已知召唤计数、关卡、英雄身份等依然由原流程负责，不因阶级识图跳过。

- 单人：`--adopt-paused` 接管先识别英雄并设tier0；后续战斗循环自动补齐。repair_one 修复的新未知阶级同样适用；操作在途不执行。每次尝试至少间隔15秒，识图后回到完整的弹窗/暂停/结算分发，不直接对旧截图操作。
- 合作：状态恢复把英雄阶级清零，reconcile 后尝试识别；先重读无遮挡战斗、身份、格子与占用必须吻合。成功后 commit/save，下一轮重新稳定观察。当前不新增“任意已占满合作战斗、无checkpoint直接接管”，那还涉及召唤总数与历史恢复，不能声称本次解决。
- 默认开启，不需更改 GUI 参数。两种 runner 都支持 `--no-visual-tiers` 关闭；旧 `--trace-tiers` 仅加旧模板日志，关闭救急应使用前者。
- 识图本身可能耗时数秒，尤其大量未知格同时走模板。只用于有未知阶级的救急，并有15秒重试间隔；尚未实测双设备性能。

这些候选现在可以触发实际合成，因此错误识别可能导致合成失败或后续跟踪出错。用户已接受这类不确定性，不应加回每次确认弹窗；也不要说已完成实战验收。

## 11. 推荐后续顺序

1. 用户需要救急时先实用当前默认接入，收集识图前截图、原始候选、实际操作后变化，别长时间只重构。
2. 建新测试集：多个英雄/皮肤、所有阶级、前排偏移、光环、怪物越界、武器露出、不同分辨率；把开发集和保留测试集明确分开。
3. 对真实三人遮挡视频做时序配准，利用特效消退后可见部位；不要仅重复同一静态错误投票。
4. 把前排同一平移下的多部件合并为人物占据区域，寻找脚底/身体下缘或稳定锚点，再校准二/三人位置；跨格比对需允许尺度、动画差异。
5. 后排只露出武器/发饰时，联合多个片段的位置与同源外观；单个通用武器不能独自证明第三人。详情点击可以确认英雄、占用及可能的阶级信息，但要核实详情实际显示什么。
6. 持续保留未知输出、误报/漏报统计与来源；用户接受救急不准不等于可以把未知强填为一阶或报告虚假的准确率。
